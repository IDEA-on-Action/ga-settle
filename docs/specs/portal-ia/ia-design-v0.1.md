**작성자:** 생각과 행동 (IDEA on Action)
**상태:** 🔧 설계 + 공개 레이어 구현 (SPEC F-054 / REQ-075·076)
**범위:** IA 설계 산출물 + 공개 레이어(홈·개요·진행현황·산출물) 서버 렌더 구현. 보호 영역(자료실·소통)은 로그인 유도까지, 상세 콘텐츠 관리는 후속 F-item.

## 1. 요약

`https://ata.minu.best/` 루트를, **계약 → 개발 → 검수 → 운영** 전 단계를 고객과 함께 보는 **협업 포털**로 재설계한다. 현재 루트는 데모 랜딩(F-032), 실 기능은 인증 뒤 `/app`(F-024)에 있고, 고객 제공 자료·이메일·피드백은 리포지토리(`docs/specs/고객제공자료/`)에 흩어져 있어 고객이 직접 볼 수 없다. 이 문서는 그 흩어진 것들을 **한 공간의 정보구조**로 묶는 사이트맵·화면구조·콘텐츠 모델·접근권한을 정의한다.

핵심 설계 원칙 3가지:
1. **라이프사이클이 1급 축이다** - 모든 정보(자료·산출물·소통)는 계약/개발/검수/운영 단계에 매달린다.
2. **공개 링크 + 일부 보호** - 진행 현황·산출물 목록은 로그인 없이 링크로 열람, 파일 다운로드·민감 자료·피드백 작성은 인증 뒤(F-024 재활용).
3. **단일 진실원천 재사용** - 진행 상태는 SPEC.md의 F-item/Sprint에서, 실 기능은 `/app`에서 링크로 끌어와 이중 관리를 피한다.

## 2. 목표 · 비목표

### 목표
- 고객(ATA 담당자)이 로그인 부담 없이 **프로젝트가 지금 어디까지 왔는지** 한눈에 본다.
- 계약·검수 단계의 **커뮤니케이션(이메일·통화·피드백)이 기록·정리**되어 소실되지 않는다.
- 고객 제공 자료와 우리 산출물이 **분류·보관·다운로드** 가능한 형태로 한곳에 모인다.
- 피드백이 **항목 단위로 접수→반영 추적**된다 (260710 시책 피드백 5건처럼).

### 비목표 (이번 설계 범위 밖)
- 실제 구현(컴포넌트·API·DB) - 계약 확정 후 별도 F-item.
- 정산 실 기능(`/app`) 재설계 - 그대로 두고 포털에서 링크만.
- 다중 고객/테넌트 - 현재는 ATA 단일 프로젝트 전제(확장은 §9 참고).

## 3. 사용자 · 핵심 시나리오

| 페르소나 | 목적 | 주요 행동 |
|---|---|---|
| **고객 담당자** (ATA 김혜경 차장) | 진행 확인·자료 열람·피드백 | 진행 현황 보기, 산출물 다운로드, 자료 업로드, 피드백 작성/확인 |
| **내부** (생각과 행동) | 진행 갱신·자료 관리·응답 | 산출물 등록, 진행 상태 갱신, 고객 자료 정리, 피드백 반영 표시 |
| **비로그인 방문자** (링크 수신자) | 공개 진행/산출물 확인 | 공개 링크로 진행 현황·산출물 목록 열람(다운로드는 인증 유도) |

**대표 시나리오**
- S1. 고객이 공유받은 링크로 들어와 "지금 검수 단계, 산출물 3건 준비됨"을 로그인 없이 확인 → 다운로드 클릭 시 로그인 유도.
- S2. 고객이 시책안 PDF를 자료실에 올리고 "이 파일 인식 확인 요청" 피드백 작성 → 내부가 반영 후 상태를 '반영됨'으로 전환.
- S3. 계약 협의 이메일을 소통 로그에 백업 → 계약 단계 타임라인에 자동 표시.

## 4. 라이프사이클 모델 (정보의 1급 축)

```
[계약] ──▶ [개발] ──▶ [검수] ──▶ [운영]
  │          │          │          │
  ├ 제안/견적  ├ 스프린트   ├ 데모/UAT   ├ 배포/모니터링
  ├ 계약서     ├ F-item    ├ 피드백     ├ 운영 리포트
  └ 소통로그   └ 산출물     └ 결함/반영   └ 이관/교육
```

각 단계는 공통 4속성을 갖는다: **상태**(예정/진행/완료), **기간**, **산출물 목록**, **소통 지점**. 자료·피드백·산출물은 반드시 한 단계에 소속된다(교차 참조 허용).

## 7. 콘텐츠 모델 (5영역 엔티티)

요청 5영역 → 엔티티 매핑:

| # | 요청 영역 | 엔티티 | 핵심 필드 |
|---|---|---|---|
| ① | 이메일 백업·피드백 정리 | `CommunicationLog` | 일시, 방향(수신/발신), 채널(email/통화/메신저), 제목, 요약, 원문/첨부, 단계, 정리상태 |
| ② | 고객 제공 자료 보관 | `Asset` | 파일명, 분류(원수사/시책안/계약/기타), 업로더, 제공일, 버전, R2키, 단계 |
| ③ | 진행 상태 보고 | `Milestone` + `Stage` | 단계, 제목, 상태(예정/진행/완료), 일자, 링크(F-item/PR), 공개여부 |
| ④ | 피드백 공간 | `FeedbackThread` | 항목, 작성자, 상태(접수/검토/반영/보류/반려), 우선순위, 연결 F-item, 코멘트 |
| ⑤ | 산출물 계획+다운로드 | `Deliverable` | 제목, 유형(문서/코드/데이터/가이드), 계획일, 상태(계획/작성중/완료), 버전, 파일, 공개여부, 단계 |

### 관계도

```
Project(ATA)
  └─ Stage[계약·개발·검수·운영]
        ├─ Milestone*        (③ 진행 보고)
        ├─ Deliverable*      (⑤ 산출물)
        ├─ Asset*            (② 고객 자료)
        ├─ CommunicationLog* (① 이메일/통화 백업)
        └─ FeedbackThread*   (④ 피드백)  ──▶ (연결) SPEC F-item
```

- **모든 엔티티는 Stage에 소속** → 진행 현황(§6)이 단계별로 롤업된다.
- **FeedbackThread ↔ F-item 연결** → 260710 피드백처럼 "접수→F-item 등록→반영→완료"가 추적된다.
- **Deliverable/Asset은 R2 보관** → 파일 불변·감사(기존 uploads/incentive-plans 패턴 재사용).

## 8. 접근 권한 모델 (사용자 결정: 공개 링크 + 일부 보호)

| 영역 | 공개(비로그인, 링크) | 인증(F-024) | 근거 |
|---|:---:|:---:|---|
| 프로젝트 개요 `/overview` | ✅ 열람 | - | 민감정보 없음 |
| 진행 현황 `/status` | ✅ 열람 | - | 상태·마일스톤은 공유 가치 |
| 산출물 **목록** `/deliverables` | ✅ 제목·상태 | - | 무엇이 준비됐는지 |
| 산출물 **파일 다운로드** | 🔒 유도 | ✅ 다운로드 | 자료 유출 방지 |
| 자료실 `/assets` | 🔒 | ✅ 열람·업로드 | 고객 원본·민감 |
| 소통 `/comms`(이메일·피드백) | 🔒 | ✅ 열람·작성 | 협의 내용 민감 |
| 실 시스템 `/app` | 🔒 | ✅ | 기존 게이트 |

**구현 방향(설계 수준)**
- 공개 라우트: `run_worker_first` + 공개 페이지 화이트리스트(`/`, `/overview`, `/status`, `/deliverables` 목록 API). **WAF 주의**: `ata.minu.best`는 Pro zone Super Bot Fight Mode가 공개 API를 막을 수 있어, 공개 엔드포인트도 WAF Skip 규칙 범위 확인 필요([[cloudflare-worker-custom-domain-waf]]).
- 보호 라우트: 기존 전역 `/api/*` 인증 게이트(F-024) 뒤. 다운로드/자료/피드백 API는 게이트 유지.
- **공개 링크 옵션(선택)**: 로그인 없이도 특정 고객에게 진행 현황을 열려면, 추측 불가 토큰 기반 공유 링크(`/p/{token}`) 방식 추가 검토(민감영역은 여전히 로그인). 이번 설계는 "공개 라우트 + 다운로드 보호"를 기본안으로, 토큰 링크는 대안으로 명시.

## 9. 현행 자산과의 관계 · 이관 방침

| 현행 | 관계 | 방침 |
|---|---|---|
| 루트 데모 랜딩 (F-032, `src/demo.ts`) | 흡수 | 포털 홈의 "데모 체험" 섹션으로 이동, 루트는 포털 홈 |
| 정식 SPA (B-006, 미완) | 별도 레이어 | 포털=고객 협업, `/app`=운영 도구. 포털에서 `/app` 링크 |
| 인증 게이트 (F-024) | 재사용 | 보호 영역 인증에 그대로 사용 |
| `docs/specs/고객제공자료/` | 데이터 소스 | 자료실(Asset)·소통로그의 시드 소스. 웹 노출 시 선별 |
| 이메일 초안(`고객메일_초안_*`) | 데이터 소스 | 소통 로그(CommunicationLog 발신) 이관 후보 |
| SPEC.md F-item/Sprint | 데이터 소스 | 진행 현황(Milestone) 롤업 원천 - 이중관리 금지 |
| 사용 가이드 (F-034, `/guide`) | 링크 | 포털 footer/산출물에 연결 |

> **단일 진실원천 원칙**: 진행 상태는 SPEC.md에서 파생(수동 재입력 금지), 파일은 R2, 실 기능은 `/app`. 포털은 이들을 **모으고 보여주는 레이어**이지 새 SoT를 만들지 않는다.

## 10. 오픈 이슈 · 다음 단계

### 결정 필요 (리뷰에서)
1. **홈 승격 시점** - 계약 전에도 루트를 포털로 바꿀지, 계약 후 전환할지 (현재 루트는 고객 데모 접속 경로).
2. **공개 범위 세부** - 진행 현황을 완전 공개할지, 토큰 링크(`/p/{token}`)로만 열지.
3. **진행 현황 자동화 수준** - SPEC.md 자동 롤업 vs 수동 큐레이션(고객 대상 문구 다듬기).
4. **다중 고객 확장 여부** - ATA 단일 전제 유지 vs 처음부터 멀티 프로젝트 구조.
